## What is it

**firsthand** is a multi-agent product-experience simulator. You give it the URL of your own product (plus an optional product manual). A lead agent generates a cohort of personas, each with their own identity, background, personality and daily schedule. On a simulated timeline, each persona uses your product in a **real cloud browser** during their own time slots, then talks about it in a Reddit-style community. The output is a strengths-and-weaknesses report in which **every conclusion is backed by evidence**.

The overall pipeline is inspired by [MiroFish](https://github.com/666ghj/MiroFish). The key difference: MiroFish agents *imagine* from source material; firsthand agents speak — or stay silent — based on what they *actually experienced*.

### Principles

1. **No experience, no voice.** Every agent must really use the product. Without a verified experience, an agent can only read posts.
2. **Per-persona observation rights.** Everything is captured (screenshots, DOM, console, network), but each persona only sees what fits who they are — a non-developer never opens the console.
3. **Every claim is traceable.** Issues and highlights must cite screenshots, steps or verbatim quotes; anything without evidence is left out of the report.
4. **What's said ≠ what's felt.** Some personas hold back, some only lurk. The report shows both the *public voice* and the *silent signals* (private exit surveys, withheld content).
5. **Measure, don't trust.** Before each run, tool calling, structured output, vision, context length and concurrency are probed — the model's self-description is never taken at face value.

## Features

- **A URL is enough to start.** Only `url` and `allowed_domains` are required in the manual. The less material you give, the more clearly the UI and report are labelled "limited reliability".
- **Recommended scale.** The lead agent recommends a cohort size (2–99) and a duration (1–365 days); you confirm or change them before personas are generated.
- **Multi-dimensional personas.** A dimension matrix guarantees coverage (age, occupation, device, tech level, patience, motivation, schedule, participation style, candor …). Each persona also gets its own sampling parameters derived from their personality.
- **Human review gate.** Personas, schedules and run configuration must be approved by you before any browsing or discussion cost is incurred.
- **Real browsing.** [Browser Use](https://github.com/browser-use/browser-use) + [Steel](https://steel.dev) cloud browsers, one isolated session per persona with built-in recording; domain allow-lists, forbidden actions and test-account injection are all gated.
- **Social discussion.** [OASIS](https://github.com/camel-ai/oasis) in Reddit mode, interleaved with browsing slice by slice. Some post, some only comment, some only upvote, some just lurk.
- **Report Agent.** The model writes the issue list and highlights, which must pass an evidence gate (citation exists, quotes are verbatim, evidence type matches). All other sections are generated by code from the full record.
- **Web UI.** New run → review → live progress → report. Click an issue to jump to the matching moment in the session recording and screenshot, with console / network summaries.
- **Interviews.** Ask any persona follow-up questions; answers cite their own experience.
- **Multiple providers.** Generic OpenAI-compatible, DeepSeek and Xiaomi MiMo adapters; Chat Completions and Responses APIs. Text-only (non-vision) models can complete the whole pipeline, with results marked as limited reliability.

## How it works

```
⓪ Capability probe   → abort if no tool calling; without vision, continue only after you
                       accept "limited reliability"
① Read the manual    → validate → lead agent builds a product model
                       (with only a URL, it reads the site's landing page)
② Personas, schedules and run config → [HUMAN REVIEW]
③ Timeline simulation (per time slice)
     a. personas whose slot has come use the product in a cloud browser
        → Experience Memory (with evidence)
     b. active agents act in OASIS: read / post / comment / upvote / do nothing
④ Exit survey        → everyone answers privately, lurkers and withholders included
⑤ Report Agent       → public voice + silent signals, every item with evidence
⑥ Interviews         → question any persona individually
```

## Quick start

### Requirements

| Component | Requirement |
|---|---|
| Python | 3.12 (browsing, API) and 3.11 (OASIS; `camel-oasis` requires `<3.12`). [uv](https://github.com/astral-sh/uv) recommended |
| Node.js | 20.19+ or 22.12+ (required by Vite 8) |
| Model | An OpenAI-compatible endpoint that **supports tool calling**; vision recommended |
| Browser | A [Steel](https://steel.dev) API key (cloud browsers and recordings) |

### 1. Clone and create the two Python environments

Browsing and OASIS have conflicting dependencies, so they live in two virtual environments inside `backend/`:

```bash
git clone https://github.com/JiaMingWang-CN/firsthand.git
cd firsthand/backend
uv venv --python 3.12 .venv-browsing
uv venv --python 3.11 .venv-oasis
```

Windows:

```powershell
uv pip sync --python .venv-browsing/Scripts/python.exe browsing/requirements.lock.txt
uv pip sync --python .venv-oasis/Scripts/python.exe discussion/requirements.lock.txt
```

macOS / Linux:

```bash
uv pip sync --python .venv-browsing/bin/python browsing/requirements.lock.txt
uv pip sync --python .venv-oasis/bin/python discussion/requirements.lock.txt
```

### 2. Configure

```bash
cp config/.env.example config/.env
```

Fill in at least the following (see [`backend/config/.env.example`](backend/config/.env.example) and [`docs/providers.md`](docs/providers.md) for details):

| Variable | Meaning |
|---|---|
| `LLM_PROVIDER` | `openai_compatible` / `deepseek` / `mimo` |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | Model endpoint, key and model name |
| `LLM_API` | `chat_completions` or `responses` |
| `LLM_THINKING_TYPE` | `enabled` / `disabled`; empty uses the server default |
| `LLM_MAX_CONCURRENCY`, `BROWSER_MAX_CONCURRENCY` | Global concurrency limits for model calls and browsers (shared across processes) |
| `STEEL_API_KEY` | Steel cloud browser |
| `TEST_ACCOUNT_<ROLE>_USERNAME` / `_PASSWORD` | Optional: test accounts declared in the manual, injected into the browser only for allowed domains |

`config/.env` is git-ignored — never commit it.

### 3. Install the frontend and start

From the repository root:

```bash
npm --prefix frontend install
npm run dev
```

This starts both the API (`127.0.0.1:8000`) and the UI (<http://localhost:5180>). Click **New run**, enter a URL and follow the flow: analyze → confirm cohort size and duration → generate personas → review and approve → simulate → read the report.

> On first use, run the capability probe to make sure the model, Steel and OASIS are all reachable (from `backend/`):
>
> ```bash
> .venv-browsing/Scripts/python.exe -m orchestrator.phase0
> ```

## Command-line usage

Run everything from `backend/` (on macOS / Linux replace `Scripts/python.exe` with `bin/python`):

```powershell
# ⓪ Capability probe (model / Browser Use + Steel / OASIS)
.venv-browsing/Scripts/python.exe -m orchestrator.phase0

# ① Validate a manual; ② generate a persona draft (everything needed for review)
.venv-browsing/Scripts/python.exe -m orchestrator.phase1 validate path/to/manual.md
.venv-browsing/Scripts/python.exe -m orchestrator.phase1 prepare  path/to/manual.md

# ③④ Timeline simulation (browsing + discussion + exit survey) from an approved draft
.venv-browsing/Scripts/python.exe -m orchestrator.phase4 runs/<approved-draft-dir>

# ⑤ Generate the report
.venv-browsing/Scripts/python.exe -m orchestrator.phase5 runs/<simulation-dir> --capability-run runs/<capability-dir>

# API only (read-only run data + interviews); interactive docs at /api/docs
.venv-browsing/Scripts/python.exe -m api --port 8000
```

Options, outputs and acceptance criteria for each phase are documented in [`docs/`](docs/) (Chinese).

## Product manual

A manual is Markdown with YAML front matter; see the template [`docs/product_manual_template.md`](docs/product_manual_template.md). Minimal example:

```markdown
---
url: https://staging.example.com
allowed_domains:
  - staging.example.com
---
```

The body may optionally describe positioning, target users, core features, key flows and **known issues**. Known issues act as a calibration set: if the agents can't even find those, the personas or browsing configuration need work. A full example is [`docs/examples/wjm_product_manual.md`](docs/examples/wjm_product_manual.md) (the author's personal website).

## Testing

```bash
# Backend (from backend/)
.venv-browsing/Scripts/python.exe -m pytest tests -q

# Frontend (from frontend/)
npm test
```

Tests never call a real model or browser; no keys are needed.

## Cost and safety

- **It costs money.** A run makes many model calls (browsing steps may carry screenshots) and uses Steel browser time. Before the review gate, only analysis and persona generation are billed. Every run records request counts and token usage (prices are not computed).
- **Only test products you are authorized to test.** Prefer a staging environment and dedicated test accounts. Agents can only visit `allowed_domains`; by default they may not make real payments or orders, delete accounts or data, send outbound messages, or submit real personal information.
- **Run artifacts are private.** `backend/runs/` contains sessions, recording links and full network traces. The API listens on `127.0.0.1` and only accepts a local `Host` header by default — do not expose it to the internet.
- **A simulation is not real users.** Use the results to find problems and form hypotheses, not as a substitute for user research. Reports explicitly flag limited reliability when material is thin or a text-only model is used.

## Known limitations

- v1 uses a single model; mixing models and accessibility personas (e.g. screen-reader users) are out of scope for now.
- Only the browser-side time zone is simulated; the site's server clock is not changed.
- The Scout pass (one browsing session that checks the manual against the real site) is not implemented yet.
- The UI and docs are currently in Chinese.

See the risks section of [`docs/plan.md`](docs/plan.md) and the "known limitations" in each phase document for more.
