## 1. 项目定位

用户提供**自己产品**的使用说明，由主 Agent 生成 10 个 Persona。每个 Persona 都有完整的身份、背景、性格和作息。他们在模拟时间线上各自的时段内，用云端浏览器**真实使用产品**，并在 OASIS 中社交讨论。最终输出一份**每条结论都附证据**的产品优缺点报告，其中既包括**说出来的声音**，也包括**没说出来的体验**。

整体流程参考 MiroFish。核心区别在于：MiroFish 的 Agent 根据材料"想象"，本项目的 Agent 根据"亲身经历"发言或保持沉默。

### 核心原则

1. 每个 Agent 都必须真实体验过产品；**没有体验过的 Agent 只能看帖，不能发言**。
2. 不同 Persona 有不同的观察权限：底层采集全部数据，但每个 Agent 只能按权限看到其中一部分。
3. 每条结论都必须能追溯到证据。
4. 模型能力以实测结果为准，不相信模型的自我声明。
5. 公开表达不等于真实体验：报告必须同时呈现"说出来的"和"体验了但没说的"。
6. Browser Use 负责"怎么操作"，OASIS 负责"这个人是谁、为什么这么做、什么时候做、之后怎么讨论"。

## 3. 整体流程

```
⓪ 模型能力探测   → 识图或工具调用不支持 → 中止
① 上传使用说明   → 校验必填项 → 主 Agent 解析出产品模型
② Scout 侦察     → 用一个浏览会话核对说明书与真实网站（不一致之处本身就算一条发现）
③ 生成 Persona、作息和运行配置 → 【人工审核关卡】
④ 时间线模拟（体验和讨论交织进行）
     每个模拟时间片：
       a. 按作息，到了体验时段的 Persona 开始真实浏览 → 写入 Experience Memory
       b. 当前活跃的 Agent 在 OASIS 中行动（看帖 / 发帖 / 评论 / 点赞 / 什么都不做）
⑤ 离场问卷       → 所有 Persona 私下作答（包括潜水者和隐瞒者）
⑥ Report Agent   → 生成报告：公开声音 + 沉默信号，每条附证据
⑦ 采访           → 可以单独追问任意一个 Persona
```

与 MiroFish 的阶段对照：

| MiroFish | 本项目 |
|---|---|
| 种子材料 → 构建知识图谱 | ① 使用说明 → 产品模型 |
| 生成人设和模拟配置（含活跃时段） | ③ Persona、作息、配置 + 人工审核 |
| — | ② Scout，④a 真实浏览体验（本项目独有） |
| OASIS 时间线模拟 | ④b 以真实体验为基础的 OASIS 讨论 |
| — | ⑤ 离场问卷（捕捉沉默的部分） |
| Report Agent | ⑥ Report Agent |
| 深度互动 | ⑦ 采访 Persona |

## 4. 模块设计

### 4.1 模型能力探测

每次运行前执行，结果写入 `capability_profile.json`。

| 探测项 | 方法 | 不支持时的处理 |
|---|---|---|
| 基础对话 | 一句话问答 | 中止 |
| 工具调用 | 单工具调用；`tool_choice` 强制指定；多工具并行调用；检查参数是否符合 schema | 单工具调用都不支持则**中止**（Browser Use 和 OASIS 都依赖工具调用） |
| 结构化输出 | `response_format` / JSON Schema | 改用"提示词约束 + 解析后校验重试" |
| 识图 | 发送一张带随机内容的图片，要求模型识别 | **中止**（本版要求必须支持识图） |
| 视频 | 短视频内容问答 | 回放分析改用截图序列 |
| 语音 | 音频内容问答 | 仅当产品本身有音频功能时才需要，否则忽略 |
| 上下文长度 / 延迟 / 并发 | 逐步增大输入；同时发 10 个请求 | 据此决定并发数、历史压缩策略和超时设置 |

测试样本都带随机答案，防止模型蒙对或假装看到了内容。

### 4.2 产品使用说明

- 格式见 [`product_manual_template.md`](product_manual_template.md)：YAML front matter 放机器读取的字段，正文用固定标题。
- 主 Agent 先校验完整性，缺少必填项时直接退回，并说明缺了什么。
- "已知问题"作为**校准集**：如果 Agent 连已知问题都发现不了，说明 Persona 或浏览配置有问题。

### 4.3 主 Agent

1. **解析说明书**，生成产品模型（功能、流程、目标人群）。第一版用结构化 JSON，暂不引入 GraphRAG。
2. **Scout 侦察**：用一个浏览会话快速走一遍网站，核对说明书与实际产品。
3. **生成 Persona**（见 4.4）：先用维度矩阵保证覆盖面，再由 LLM 补全身份、背景、性格等细节，并保证人物前后自洽。
4. **生成运行配置**：时间线长度、时间片粒度、各人作息与体验时段、并发上限。
5. **人工审核**：把 Persona 列表、作息时间表和配置展示给用户，用户可以编辑，确认后才开始执行。

### 4.4 Persona 维度

| 类别 | 维度 | 说明 |
|---|---|---|
| **身份** | 名称（realname / username）、性别、年龄、所在城市、时区 | 时区决定作息对应的本地时间 |
| **背景** | 职业、行业、教育程度、收入水平、生活状态、与本产品相关的经历（比如用过哪些竞品、为什么来用） | 背景要能解释这个人的动机和期望 |
| **性格** | MBTI、大五人格的关键维度（开放性、尽责性、外向性、宜人性、神经质）、沟通风格（直接 / 委婉 / 爱吐槽 / 爱夸） | 影响操作耐心、表达方式和隐瞒倾向 |
| **使用特征** | 技术水平（小白 / 普通 / 开发者）、设备（手机 / 桌面）、耐心（低 / 中 / 高）、动机（随便看看 / 有明确任务 / 对比竞品 / 付费决策）、账号状态（新访客 / 免费用户 / 付费用户） | 会换算成浏览阶段的硬约束 |
| **作息** | 起床和睡觉时间、各时段的活跃度、体验产品的时段、刷社区的频率 | 见 4.6 |
| **参与方式** | 发帖者 / 评论者 / 点赞者 / 潜水者 | 见 4.9 |
| **表达意愿** | 坦率程度、隐瞒倾向、可能隐瞒的原因 | 见 4.9 |
| **任务分配** | 指定的关键流程，或自由探索 | 每个关键流程至少分给 2 人；约 30% 的人自由探索 |

10 人的分布约束（主 Agent 生成时必须满足，用户审核时可以调整）：
- 至少 2 名开发者，至少 4 名手机用户，至少 3 名低耐心用户。
- 性别和年龄段要分散，并与说明书中的"目标用户"分布大致吻合。
- 参与方式大致为：发帖者 3、评论者 3、点赞者 2、潜水者 2。
- 至少 2 人有明显的隐瞒倾向。
- 体验时段要覆盖一天中的多个时间段（早、午、晚、深夜）。

### 4.6 时间线与作息

- **模拟时间线**：默认模拟 1 天，时间片为 1 小时，可以配置（比如 3 天，每片 30 分钟）。这里用的是逻辑时钟，与现实时间无关。
- **体验时段**：每个 Persona 在自己的 `browse_slot` 开始真实浏览。体验时的状态会注入提示词，比如"深夜很困"会导致耐心下降、更容易放弃。
- **浏览器环境与时段对齐**：
  - 通过 CDP 的 `Emulation.setTimezoneOverride` 设置时区和语言区域。
  - 产品里与时间相关的内容（问候语、营业时间、活动）会随之变化。
  - 现实中的服务端时间无法模拟，在报告中注明这一点。
- **社区活跃**：在每个时间片，按 `activity_by_hour` 的概率决定当前有哪些 Agent 活跃，活跃的 Agent 才在 OASIS 中执行一步。
- **体验前与体验后的权限**：
  - 体验产品之前：只能看帖，不能发帖或评论。但看到的帖子会被记入记忆，作为"先入为主的预期"，体验时可以拿来对照，比如"看到有人说注册很麻烦，我自己试了发现还好"。
  - 体验产品之后：按照各自的参与方式行动。
- **编排方式**：由 Orchestrator 统一推进时钟。每个时间片内，先完成该时段的浏览（同一时段的多个浏览会话并发执行），再调用 OASIS 执行一步。浏览进程和 OASIS 进程通过 SQLite 交换数据，按时间片同步。
- **并发**：所有模型请求共享环境中的模型上限；浏览 Agent 并发取模型与浏览器上限的较小值，浏览器上限需匹配 Steel 套餐。人设生成、讨论等不使用浏览器的模块仅占模型额度。如果同一时间片要浏览的人数超过上限，就在该时间片内排队，逻辑时钟不受影响。

### 4.7 浏览执行层

- 每个 Persona 对应一个 Steel Session 和一个 Browser Use Agent。Persona 的人设、当前状态，以及体验前看到的帖子，都写进 Agent 的提示词。
- **旁路采集**：另开一条 CDP 连接，全量记录 Console、Network、性能数据和截图，写入 Raw Trace。同时保存 Steel 录像的链接。
- **约束执行**：`max_steps` 和 `stall_limit` 由框架强制执行，不能只写在提示词里。视口按 `device` 设置，时区按 `timezone` 设置。
- **安全措施**：
  - 设置域名白名单，超出范围的导航一律拦截。
  - `forbidden_actions` 中的操作一律拒绝执行，并记为一条体验。
  - 测试账号通过 `.env` 和 Browser Use 的敏感数据机制注入，LLM 看不到明文。
  - 遇到验证码或反爬时记为一条体验，不尝试绕过。

### 4.8 观察权限网关

| 角色 | 能看到什么 | 额外工具 |
|---|---|---|
| 普通用户（小白 / 普通） | 页面（截图 + DOM）和交互结果 | 无 |
| 开发者 | 普通用户能看到的全部 | `read_console`、`list_failed_requests` 等 Console / Network 查询工具 |

Steel 和旁路 CDP 采集全部数据，但只有被授权的 Agent 才能通过工具看到其中的技术数据。

### 4.9 Experience Memory、表达与沉默

**Experience Memory**（每个 Persona 一份，**完整记录，不受表达意愿影响**）：
- 步骤日志：每一步的操作、URL、耗时、截图引用
- 任务结果：成功 / 失败 / 放弃，以及原因
- 情绪曲线：每一步的满意度和困惑度
- 痛点与亮点：每一条都附证据（步骤编号、URL、截图、报错、录像时间点）
- 体验前的预期：体验前看过哪些帖子、当时有什么预期，以及实际体验是否符合预期

**表达过滤**（Agent 发言时）：
- Agent 发帖或评论之前，先根据性格和 `disclosure` 设置，用结构化输出决定这次讲什么：
  ```yaml
  shared:   [痛点1, 亮点2]
  withheld:
    - item: 痛点3（找不到导出按钮）
      reason: 怕显得自己不会用
  ```
- `withheld` 写进数据库，不发到 OASIS 上。

**参与方式在 OASIS 中的实现**：给不同的 Agent 开放不同的动作集合。

| 参与方式 | 可执行的动作 |
|---|---|
| 发帖者 | 看帖、发帖、评论、点赞或点踩 |
| 评论者 | 看帖、评论、点赞或点踩 |
| 点赞者 | 看帖、点赞或点踩 |
| 潜水者 | 只能看帖（以及什么都不做） |

所有 Agent 的看帖记录都会保存（看了哪些帖子、什么时候看的），用来分析讨论对他们观点的影响。

### 4.10 离场问卷

时间线结束后，**所有 Persona 都私下作答**，包括潜水者和隐瞒者。问卷是匿名的，不会公开：
- NPS（愿意推荐的程度），以及会不会继续使用、会不会付费
- 最大的问题和最喜欢的点
- 有没有想说但没说的话，以及为什么没说
- 讨论有没有改变你的看法，是哪条帖子改变的

问卷答案要和 Experience Memory 做一致性校验，不一致的地方要标记出来。

### 4.11 Report Agent

- 采用 ReACT 加工具的方式：可以查询 Experience Memory、`withheld` 记录、讨论内容、看帖记录、离场问卷和录像时间点，边查边写。
- **问题的排序**：按"影响了几个人 × 严重程度 × 证据强度"排序，**不按讨论中的点赞数排序**。
- **报告结构**：
  1. 总览：任务完成率、NPS，以及覆盖说明（哪些部分没有覆盖，比如服务端时间无法模拟）
  2. 问题清单：按优先级排列，每条都附证据和受影响的 Persona
  3. 亮点
  4. **公开声音与沉默信号**：
     - 社区里说出来了什么
     - 体验了但没说的（来自 `withheld` 记录和潜水者的数据），以及没说的原因
     - 公开讨论的结论与私下问卷是否一致
  5. 舆论动态：观点是怎么传播的，哪些帖子影响了别人的预期或评价
  6. 分时段的体验差异：不同时段、不同状态下的体验有什么不同
  7. 说明书与实际产品的不一致之处（来自 Scout）

### 4.12 采访

运行结束后，可以向任意一个 Persona 提问。它会基于自己的 Experience Memory 和讨论记录，以自己的人设风格回答。隐瞒者在采访中也可能继续回避，这一点符合真实情况。但报告不依赖采访内容，因为报告直接读取完整记录。

## 5. 工程结构

- 全部用 Python。
- **浏览器只通过 Browser Use 操作和采集，不使用 Playwright**。旁路采集（Console、Network、截图、性能、时区）复用 Browser Use 自己的 CDP 连接。原因：多个 CDP 客户端同时连接同一个 Steel 会话时会互相干扰（实测出现重复响应）。注意两点：
  - cdp_use 对每个事件只保留一个处理函数，不能注册 Browser Use 已经占用的事件（例如 `Network.responseReceived`），否则会悄悄覆盖它的处理逻辑。
  - 不使用 Browser Use 内置的 HAR 记录：它会对每个请求都去拉取响应正文，导致 Steel 连接因心跳超时而断开。
- **两个进程、两个 venv**：OASIS（camel-oasis）与 browser-use 的依赖可能冲突，所以分开。由 Orchestrator 推进时钟，进程之间通过 SQLite 交换数据。
- 编码前用 Context7 或探针脚本核对以下几点：
  - browser-use、steel-sdk 的当前 API
  - camel-oasis 的 OpenAI 兼容模型接入方式
  - 能否按 Agent 限制动作集合
  - 能否由外部逐步驱动 `env.step`
  - 能否手动执行发帖等动作

```
muchhuman/
├── docs/                  # 方案与各阶段记录（前后端共用）
├── frontend/              # Web UI：Vue 3 + Vite（阶段 6）
└── backend/               # Python 项目根；所有命令都在此目录下执行
    ├── config/            # .env.example、模型配置
    ├── core/              # 共享数据结构（Persona、Experience Memory、运行配置）
    ├── probe/             # ⓪ 模型能力探测
    ├── orchestrator/      # ①②③ 主 Agent、说明书解析、Persona 生成、审核、时钟推进
    ├── browsing/          # ④a 浏览执行层（venv A：browser-use + steel）
    ├── discussion/        # ④b OASIS 讨论（venv B：camel-oasis）
    ├── report/            # ⑤⑥⑦ 离场问卷、Report Agent、采访
    ├── api/               # 阶段 6：FastAPI 接口层（只读运行目录 + 采访）
    ├── tests/
    └── runs/<run_id>/     # 每次运行的产物：db、trace、截图、报告（不入库）
```

前后端分离：前端只通过 HTTP 访问 `api/`，不直接读 `runs/`。`.venv-browsing`、`.venv-oasis` 与 `.runtime/` 位于 `backend/` 内（不入库），文档中的 `.venv-*/Scripts/python.exe`、`runs/…`、`config/…` 均相对 `backend/`。

## 6. 开发阶段

| 阶段 | 内容 | 验证标准 |
|---|---|---|
| 0 | 模型能力探测；Steel + Browser Use 连通，加上旁路采集和时区设置；用自定义模型跑通一个最小的 OASIS Reddit 模拟，并验证按 Agent 限制动作集合和外部驱动 step | 三项技术验证都跑通；模型不支持识图时能够正确中止 |
| 1 | 说明书模板与校验；主 Agent 生成产品模型、Persona（全部维度）、作息和配置；审核界面（先用 CLI） | 用一份真实说明书生成 10 个人，满足 4.4 中的分布约束，人物自洽且各不相同；缺少必填项时会被拒绝 |
| 2 | 单个 Persona 浏览，生成 Experience Memory，并测试人设和状态对浏览的影响 | 每个痛点都附证据；已知问题能被发现；同一流程下"深夜疲惫的小白"与"白天的开发者"表现出明显差异 |
| 3 | 10 人按时间线浏览（含并发与排队），加上观察权限网关 | 全部跑完；非开发者没有调用过技术工具；记录单次运行的模型请求与 token 用量（不显示价格） |
| 4 | 时间线编排，体验和讨论交织；OASIS 讨论，加入参与方式、表达过滤和看帖记录；离场问卷 | 潜水者没有任何发言；`withheld` 有记录且没有出现在帖子里；体验前的 Agent 不能发言 |
| 5 | Report Agent | 报告包含"公开声音与沉默信号"一节，每条结论都附证据链接 |
| 6 | 采访功能，Web UI | 能从报告中的问题直接跳转到对应的录像片段 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 成本：10 人 × 30–80 步的识图调用，加上时间线上各 Agent 在 OASIS 中的调用 | 阶段 3、4 分别测出成本；用历史压缩、步数上限、活跃概率来控制 |
| Steel 并发受套餐限制 | 同一时间片内排队，逻辑时钟不受影响 |
| LLM 编造体验 | 每个痛点都必须附证据，没有证据的不写进报告 |
| 讨论同质化、从众 | 注入各自的体验记忆；报告不按点赞排序；离场问卷做交叉校验；多模型阶段进一步缓解 |
| 人设流于表面（只换了名字，行为一样） | 人设要换算成硬约束（步数、设备、时段状态、动作集合）；阶段 2 专门验证不同人设的行为差异 |
| 隐瞒行为不可控（LLM 倾向于什么都说） | 发言前用结构化输出强制做"讲什么 / 不讲什么"的决策，并记录下来 |
| 服务端时间无法模拟 | 只模拟浏览器端的时区，并在报告中注明 |
| 误操作造成破坏 | 域名白名单、禁止操作清单、只使用测试账号 |
| 依赖冲突 | 两个进程、两个 venv |

## 8. 后续扩展（不在 v1 范围内）

- **多模型**：按能力把 Persona 分配给不同模型（规则：Persona 需要的能力 ⊆ 模型具备的能力）。不同模型扮演不同的人，也能缓解讨论同质化。
- **盲人 Persona（无障碍）**：
  - 只能看到无障碍树（`Accessibility.getFullAXTree`），只能用键盘操作（Tab、回车、方向键、按标题或地标跳转），不能按编号点击元素。
  - 不支持识图的模型只能扮演这类 Persona。
  - 不能简单用"关掉视觉的 DOM 模式"来代替，否则会低估无障碍问题。
- **其他无障碍 Persona**：色盲（`Emulation.setEmulatedVisionDeficiency`）、低视力（200% 缩放加模糊）、只用键盘的用户、老年人。
- **扩大规模**：分层体验（核心 Persona 深度体验，扩展 Persona 只轻量体验核心流程）。所有发言者都必须真实体验过产品；没有体验过的人只能潜水。
- **知识图谱**：说明书变复杂后，再引入 GraphRAG。
