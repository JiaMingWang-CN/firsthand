# 阶段 7：只填网址、可设人数与天数、人物独立采样参数

## 进度

- [x] 7.1 后端：说明书只要求 url 与 allowed_domains；阶段 1 拆为“分析与推荐”和“按确认的人数与天数生成”；分布约束按人数换算；多天时间线；人物独立采样参数
- [x] 7.2 前端：新建运行默认“只填网址”；审核页先确认人数与天数，生成后可改天数和每人的采样参数

## 1. 资料：最少只填网址和域名

`orchestrator/manual.py` 只要求 front matter 里的 `url` 与 `allowed_domains`，其余都可以不写：

| 不写的项 | 回退 | 对结果的影响（界面、审核页与报告覆盖说明都会列出） |
|---|---|---|
| `name` | url 的域名 | — |
| `test_accounts` | 空：只有未登录的新访客 | 登录后的功能不会被覆盖 |
| `forbidden_actions` | 默认清单 `DEFAULT_FORBIDDEN`（真实支付或下单、删除账号或数据、对外发送消息、提交真实个人信息） | — |
| 产品定位 / 核心功能 | AI 根据首页摘录推断，写入产品模型的 assumptions | 产品理解来自推断 |
| 目标用户 | — | 人群分布是 AI 的假设 |
| 关键流程 | 全部自由探索 | 重要流程可能没人走到 |

`material(manual)` 把资料分成三档：`complete`（四个正文章节都有）、`partial`、`limited`（产品定位、目标用户、核心功能都没有）。`limited` 时提示“本次结果参考性有限”。写了的章节仍按原格式严格校验：未知章节、只有占位名称的核心功能，以及没有 `## 流程：` 标题的关键流程，都会被退回。

**首页摘录**（`orchestrator/site.py`）：分析阶段用一次 HTTP GET 读取 url 的静态文字（标题、描述、正文，最多 6000 字）。跳转只在 allowed_domains 内跟随，正文最多读取 2 MB。读取失败只记录原因，不中断分析。脚本渲染的页面几乎读不到文字，这种情况会如实标注。这一步不是浏览器会话，与“浏览器只通过 Browser Use 操作”不冲突。摘录只进入生成提示词，并注明“系统读取，不是说明书原文”。

## 2. 人数与天数：主 Agent 推荐，用户确认或修改

阶段 1 拆成两步，界面与命令行走同一套步骤：

```powershell
.venv-browsing/Scripts/python.exe -m orchestrator.phase1 analyze <说明书> [--capability-run <目录>]   # 能力、首页摘录、产品模型、推荐
.venv-browsing/Scripts/python.exe -m orchestrator.phase1 generate <运行目录> --personas 40 --days 50  # 不给数字时用推荐值
.venv-browsing/Scripts/python.exe -m orchestrator.phase1 prepare <说明书> [--personas N] [--days D]   # 两步连做
```

- `analyze` 依次写出 `site.json`、`product.json`、`recommendation.json`，以及 `phase1_result.json`（`stage: analyzed`，含资料档位与最少人数）。推荐的提示词约定“一般 30–50 人、50 天左右”，再按产品复杂度、流程数和资料多少调整。推荐只是建议，不做数值强制。
- 人数允许 2–99（ID 为 p01–p99），天数允许 1–365。有关键流程时，人数不能低于 `minimum_count`，保证每条流程至少有人走。
- 生成失败时分析结果保留（`generation_error`），可以直接重试或换个人数。人物生成后人数固定，要换人数需新建运行。天数可以在审核时修改，但不能少于最晚的体验日。

**分布约束按比例换算**（`targets`）：开发者约 20%，手机用户约 40%，低耐心约 30%，高隐瞒倾向约 20%，自由探索约 30%；参与方式按 3:3:2:2 用最大余数法分配，允许 ±人数/20。10 人时与原来的 2/4/3/2、3 人探索、3/3/2/2 完全一致，原有测试不变。

**分批规划**：维度矩阵每次请求规划 10 个槽位，后续批次能看到已规划的槽位和全体还差的数量，避免大人数超出模型的输出上限。非最后一批只检查是否超过全体配额，最后一批检查全部约束。

**多天时间线**：槽位新增 `browse_day`，表示该人在第几天首次体验。天数大于 1 时，体验日至少分布在 3 个不同的日子。`schedule_rows` 按本地墙钟时间往后加天，跨夏令时也不偏移。每个人仍只体验一次产品，之后按作息参与讨论，直到时间线结束。旧草稿没有这个字段，按第 1 天处理。

## 3. 人物独立采样参数

每个人物有 `sampling: {temperature, top_p, presence_penalty}`，由代码根据性格推出（`derived_sampling`）：

- temperature = 0.45 + 0.15×开放性 + 0.08×外向性 + 0.08×神经质 − 0.06×尽责性 + 小偏移，等级按低 0、中 1、高 2 计
- top_p = 0.86 + 0.04×开放性 + 0.02×外向性 + 小偏移，上限为 1
- presence_penalty = 0.1×开放性 + 0.1×外向性

小偏移由人物 ID 和用户名哈希得出，范围为 ±0.05。性格相同的人参数也不同；生成时再保证每人的 (temperature, top_p) 组合都不重复。审核时可以逐人修改；修改后若出现完全相同的组合，会作为分布变更要求确认。

**使用范围**：只用于以人物身份说话的调用，包括 Browser Use 浏览（替换框架默认的 0.2）、OASIS 社区里的行动选择（每人一个 backend，原来全员 0）、表达过滤、离场问卷和采访。主 Agent 的规划、产品模型、体验评估、操作规则和报告仍使用默认值，保证结构化输出稳定。

**能力门禁**：模型探测新增 `sampling` 检查；用 Responses 时另加 `chat_completions_sampling` 检查，因为框架实际走 Chat。只有服务商接受这些参数时才发送。旧能力文件没有这项检查，就不发送，所有人仍用框架默认值；审核页和新建运行页会说明，重新探测后生效。Responses API 没有 presence_penalty，所以这一项只在 Chat 上发送。

## 4. 界面

- **新建运行**：默认“只填网址”，填网址后域名自动填好，名称、一句话定位、目标用户都是选填。表单拼出的说明书与完整说明书走同一套校验。校验结果显示资料档位，以及每一项缺失的影响。第 3 步改为“分析资料”。
- **审核页**：
  - 分析中和生成中都有进度；资料不全时始终显示缺项和首页读取情况。
  - 新增“待确认人数与天数”状态，显示推荐值和理由，输入框可改，超出范围或低于最少人数时不能生成。
  - 草稿审核时可改天数，人物表新增体验日与温度 / top_p 两列，展开一行可修改采样参数。修改带上展示版本的哈希，保存后需要重新批准。
- **其他页面**：人物页的分布要求按人数换算；人物档案显示体验日和采样参数；运行列表和任务页认识分析与生成两类任务。

## 已知限制与注意

- **没有做真实的付费端到端运行**。本阶段没有调用真实模型，分析、推荐、40 人生成和多天模拟都只用桩验证过。
- **规模**：50 天、每片 60 分钟，就是 1200 个时间片，每片都要推进一次 OASIS。活跃且已体验的人每次活跃都要做一次表达过滤和一次行动选择。40 人、50 天的模型调用量和耗时比 10 人、1 天高出两个数量级以上。浏览受 `BROWSER_MAX_CONCURRENCY` 限制（默认 1），同一时间片里要浏览的人会排队。当前不显示费用。
- **采样参数**：服务商接受参数不等于参数生效；部分模型在思考模式下会忽略温度和 top_p，审核页会提示。参数由公式推出，不是模型推荐；“AI 推荐”指人数和天数。
- 每个人在时间线上只体验产品一次；多天只用来分散首次到访、延长讨论，不模拟回访。
