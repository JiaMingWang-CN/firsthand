# 全项目审核修复

工作分支：`fix/project-audit`，审核修复完成后合并到 `main`。

## 修复内容

| 审核问题 | 修复 | 回归验证 |
|---|---|---|
| API 重启导致任务失去监控和模拟互斥 | 新增 `api.job_runner` 独立协调进程，持久化 PID、执行计划和最终状态；按 runs 根目录跨进程锁住任务预留，原子更新任务 JSON | 真实启动进程退出后，模拟与报告两个本地夹具步骤仍完成；另一个 API 视图识别运行状态，拒绝第二个模拟 |
| 同一草稿重复生成人物 | 任务锁内再次检查该草稿的活动任务与已有 draft；生成请求不能重复预留 | 两个 Jobs 实例同时请求，只有一个被接受 |
| 人数与确认值不一致 | 每批返回数量必须等于本批 size，ID 范围继续严格校验；最终总数必须等于确认人数 | 确认 3 人但返回 10 人时在生成身份前拒绝；23 人的第一、中间、最后批次都检查缺项 |
| 修改源草稿改变运行和历史展示 | 阶段 4 在任何付费工作前复制并校验审批输入到 `approved_source/`；浏览、讨论、报告、运行概览与列表都读取快照；活动任务期间禁止编辑和决策 | 修改原草稿后快照仍通过审批，历史天数与产品名称不变；浏览 worker 使用快照 |
| 社区固定 600 秒超时 | 按人数、模型并发、结构化修正/传输重试预算和行动选择预算计算批次期限，step 与 finish 都使用 | 低并发大人数获得更长期限；执行流程验证两个命令均收到该期限 |
| 安静社区被判失败 | 社交验收只判断权限、表达投影与问卷正确性，不强制制造发言或隐瞒；没有任何体验结论的运行也可完成空问题/亮点报告 | 潜水社区、零结论社区和零结论报告均通过；原有违规与伪造证据测试仍通过 |
| 4 条引用上限压低影响人数 | 取消提示词中的引用上限，要求完整引用支持结论的全部人物；计数和排序仍只基于通过门禁的引用 | 同一结论支持 6 名人物，计入全部 6 人与对应优先级 |
| 时间深链接被加载终点覆盖 | 等对应运行加载完成、跨度就绪后应用 URL 时间；加载过程中不反写 URL，失效定时器不跨运行写入 | 第 1 天和 50 天运行中的第 40 天定位都保留指定时刻 |
| 协调进程失联后没有释放入口 | 记录每个阶段子进程的 PID 与创建时间；`python -m api.abandon_job <任务 ID>` 在跨进程锁内确认任务仍失联、子进程已结束后标记为失败并释放预留；没有子进程记录的旧任务需操作者核实后加 `--force`；界面的失联提示给出该命令 | 子进程已结束的失联任务被释放后可启动新模拟；子进程仍在运行时拒绝；旧任务不加 `--force` 拒绝，CLI 加 `--force` 后释放；非失联任务拒绝 |
| PID 复用让死去的协调进程看似仍在运行 | 协调进程与子进程都按 PID 加创建时间（psutil，1 秒容差）判断存活；`psutil` 写入 browsing 依赖 | 同一 PID、创建时间不符时显示失联 |
| 加载后时钟未变时 URL 缺少时刻 | URL 回写同时响应运行就绪，不只响应时钟分钟变化 | 前一运行已停在相同终点时，打开新运行后 URL 仍写入时刻 |
| 大数组超过 JavaScript 参数数量上限 | 数组按块原地更新；重建社交事件复用该更新方式；时间范围计算用迭代替代大数组展开 | 15 万条读帖/社交事件、15 万帖子加 15 万评论均可处理 |

## 兼容与操作注意

- 新运行有完整审批快照；旧运行没有快照时仍兼容原读取方式，但界面禁止编辑其源草稿，以免修改历史展示。需要调整配置时新建草稿。已经在本次修复前被修改的历史输入不能凭空恢复。
- 旧版本留下的任务、或协调进程失联的任务显示 `detached`，继续占用模拟/草稿预留，不能据此直接启动第二个付费任务。在 backend 目录用 `.venv-browsing` 的 Python 执行 `python -m api.abandon_job <任务 ID>` 释放；子进程仍在运行时命令会拒绝。旧任务没有子进程记录，需操作者核实后加 `--force`。只检查直接的阶段进程：阶段进程被强杀后遗留的孙进程（OASIS、浏览器）需操作者自行确认。不自动重跑付费步骤。
- 独立协调器保护的是 API 重启，不承诺操作系统重启或强制杀死整个任务进程树后自动续跑。真实的大规模付费端到端运行仍需另行验收。
